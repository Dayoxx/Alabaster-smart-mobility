Fixing the gap — part 1

Driver re-verification (session model)

A driver used to bind to a vehicle once, permanently — a stolen or borrowed terminal kept operating as that driver indefinitely. Fix: operating a vehicle requires a short-lived, renewable session.

Risk closed

Whoever physically holds the terminal is no longer automatically "the driver" — a live, expiring session is required, re-confirmed on a schedule and on anomaly.

  • Shift-start check-in — fingerprint matched against the locally cached template, opens a session with a TTL.
  • Session TTL — expires after 8–12 hrs or terminal power cycle; Go rejects trip authorization on expiry.
  • Risk-triggered re-check — GPS jump or impossible velocity forces immediate re-scan mid-session.
  • Periodic re-verification — every 30–90 days, session start requires a live VSP call, not just the cache.
Fixing the gap — part 2

Device binding & receiver-only terminals

Session auth answers "is the right driver operating right now." It doesn't stop someone tampering with where the money goes — this fix closes that separately.

Device-identity binding

Each physical terminal is registered to exactly one driver at provisioning time, keyed by hardware ID — longer-lived than a session.

Receiver-only architecture

On a tap, Flutter captures the NFC UID, signs it with the device-bound key, and relays card_uid + terminal_id + nonce + timestamp. Payout destination is resolved only server-side, from the Postgres binding record.

Net effect

There is nothing on the device to edit, root, or reflash to redirect funds — the routing decision was never on the device.

Replay protection

Every tap carries a single-use signed nonce; Go rejects any nonce already consumed.

Rebinding is privileged and re-verified

Rebinding a terminal requires an admin action and the new driver's fresh fingerprint — never just a database field toggle.

Passenger security control

Physical card lifecycle

The company-issued NFC card is a payment credential, not a bank account and not a wallet. It authorizes the passenger's transport payment against one of their linked bank accounts. Passenger-controlled card state therefore sits independently from both identity state and linked-account state.

Core distinction

Card activation controls the credential. It does not activate, deactivate, freeze, or modify any linked bank account. The passenger may have up to three linked accounts while possessing one current physical transport card.

State model

ACTIVE → INACTIVE

Passenger turns the transport card off in the app. Future taps are rejected; linked bank accounts remain unchanged.

INACTIVE → ACTIVE

Passenger turns the current card back on. No new card is issued and no bank-account changes occur.

ACTIVE / INACTIVE → BLOCKED

Passenger reports the card lost, stolen, or compromised. Blocking is immediate and prevents authorization. A blocked card cannot simply be switched back on.

BLOCKED → VOID + NEW CARD ACTIVE

After identity verification at an authorized replacement point, the old credential is permanently retired and a new credential is issued to the same passenger identity.

Passenger controls

GET

Return the authenticated passenger's current card status and replacement status without exposing the card UID.

Reactivate an inactive current card. Reject if blocked or void.

Immediately block a lost, stolen, or compromised card. Record reason and timestamp.

Start or complete replacement through an authorized agent/operations flow after identity verification; never silently create a second active card.

Lost or stolen card recovery

  1. Passenger opens the app and chooses Block card.
  2. Backend authenticates the passenger and verifies the card belongs to that identity.
  3. Backend changes the card to blocked immediately and records the reason and event.
  4. Passenger can continue using their linked bank accounts only through a valid transport credential; the blocked card itself cannot authorize payment.
  5. For a physical replacement, an authorized agent performs fresh identity verification before issuing a new card.
  6. The old credential is moved to void, the new UID is bound to the same passenger identity, and the issuance/replacement event links the two credentials.
Security invariant

At most one physical card credential is active for a passenger under the normal replacement model. Old credentials are retained for audit history but can never authorize another trip.

Determined before the tap, not after

Fare engine

The payment architecture also records a driver_daily_ticket financial event keyed by driver and operating date. This keeps the daily levy auditable and separate from trip records.

The driver selects the destination, the fare shows, then the passenger taps — matching how this already works verbally ("I'm going to Terminal F"). Three things feed one lookup: a fixed fare for named terminal-to-terminal trips, a stop-count tier for intermediate stops along whichever route the driver is running that day, and a distance-band estimate for the rare case that's neither.

Why distance bands, not a live GPS meter

Every other flow in this system is pay-before-boarding — fare known and charged before the ride starts, which is also what protects the driver from a passenger who can't pay at the end. A live meter means paying after the ride, which breaks that pattern and reopens exactly the dispute risk the rest of this architecture was built to avoid. A distance band keeps the same upfront-payment guarantee, just with an estimated fare instead of an exact one — and it matches how Keke fares already work culturally: flat by rough distance, not metered.

The flow

  1. Shift start: driver picks which admin-defined route they're running today (Tanke↔Challenge, Tanke↔Ipata, Tanke↔Taiwo...) — pre-filled with their usual route, changeable daily. Stored on the session, not fixed on the vehicle.
  2. Passenger tells the driver their actual stop — often not a named terminal at all: "Tanke Oke Odo to High Court," not "Tanke to Challenge." A driver running the Tanke↔Challenge route naturally covers this, because High Court is one of the intermediate route_stops along it.
  3. Driver's terminal shows a destination picker — GetRouteDestinations returns the stops on today's chosen route, in corridor order, major and minor stops together, plus a "not on this route" option with distance-band choices for the genuine edge case.
  4. Driver selects it → GetFare looks up the matching rule → fare displays on screen.
  5. Passenger taps card or phone → AuthorizeTrip charges exactly that fare, traceable back to the exact rule via trip.fare_rule_id.

Scoping the picker — the actual mechanism

route_stop is the ordered list of terminal locations on a route — this was already built to hold many intermediate stops, not just two endpoints, so Tipper Garage, Flower Garden, and High Court are just more rows in sequence_order between Tanke and Challenge. vehicle.route_id is a default suggestion; session.route_id is what's actually used once a driver confirms or changes it for the day.

  • Ahead-of-position filtering — using the driver's live GPS ping against sequence_order, the picker drops stops already behind them.
  • Fetch once per shift, not per trip — pull the route's stops once at session start, cache client-side in Flutter for the rest of the shift.
func GetRouteDestinations(sessionID string, currentLat, currentLng float64) ([]TerminalLocation, error) {
    session := db.GetSession(sessionID)
    stops := db.GetRouteStops(session.RouteID) // today's chosen route, ordered by sequence_order

    currentSeq := nearestStopSequence(stops, currentLat, currentLng)
    ahead := []TerminalLocation{}
    for _, s := range stops {
        if s.SequenceOrder > currentSeq {
            ahead = append(ahead, s.TerminalLocation)
        }
    }
    return ahead, nil
}

One route per shift by default — matches the "fixed routes, no random roadside loading" principle from the original transport model, while still giving drivers the daily choice they asked for. Running two routes in one shift would be a real schema change (a route_id that can flip mid-session), not something this covers yet.

Route management — creating routes, ordering their stops, assigning which routes exist for drivers to choose from — is a new admin capability, privileged and web-only alongside terminal provisioning.

Fares between intermediate stops — tier by stops traversed, not by pre-priced pairs

The naive approach — an explicit fare row for every possible origin/destination pair — explodes fast. A route with 8 stops has up to 56 directed pairs; someone has to price and maintain every one. route_fare_tier avoids that: fare is computed from how many stops apart two points are on the route, using the sequence_order already on each stop, not from a lookup table sized to every combination.

Tanke Oke Odo → High Court and Tanke Oke Odo → Tipper Garage don't need two separately priced rows — they need one tier table per route (e.g. 1–2 stops = ₦150, 3–5 stops = ₦200, 6+ = ₦250), and every pair on that route prices itself automatically from where they sit in the sequence. Named-terminal fares (a full Tanke→Challenge run) can still get an explicit override in fare_rule where the business wants a specific number instead of the tier default — the tier system is the sensible default, not the only option.

// unified result regardless of which mechanism matched — this is what
// makes trip.fare_source_type / fare_source_id traceable either way
type FareQuote struct {
    FareAmount            float64
    SourceType            string // "explicit_rule" | "route_tier" | "distance_band"
    SourceID              string
    DestinationTerminalLocationID *string // nil for distance_band
}

func GetFare(sessionID, originID, destinationID string, vehicleClass string) (*FareQuote, error) {
    session := db.GetSession(sessionID)

    // explicit override first — e.g. a named full-corridor fare set deliberately
    if rule := db.FindExplicitFareRule(originID, destinationID, vehicleClass); rule != nil {
        return &FareQuote{rule.FareAmount, "explicit_rule", rule.ID, &destinationID}, nil
    }

    // same-route case — the common one — price by stops traversed
    origin, dest := db.GetRouteStop(session.RouteID, originID), db.GetRouteStop(session.RouteID, destinationID)
    if origin != nil && dest != nil {
        stopsTraversed := abs(dest.SequenceOrder - origin.SequenceOrder)
        tier := db.FindRouteFareTier(session.RouteID, stopsTraversed, vehicleClass)
        return &FareQuote{tier.FareAmount, "route_tier", tier.ID, &destinationID}, nil
    }

    // neither a named override nor a stop on today's route — genuine fallback
    band := db.FindDistanceBandFare(originID, "medium", vehicleClass)
    return &FareQuote{band.FareAmount, "distance_band", band.ID, nil}, nil
}

The 85% coverage you're aiming for is an ops question, not a schema one — the schema already supports as many route_stops as a route needs. The actual work is HQ observing real alighting patterns per corridor and populating enough intermediate stops to match them; the distance-band fallback exists precisely for whoever falls outside that 85%.

Driver operating levy

Daily ticket

Driver-controlled vehicles are subject to a daily operating levy called the ticket. The ticket is deducted from the driver's linked receiving bank account and paid to the driver's union bank account. It is not a wallet balance, and it is not deducted simply because a driver exists in the system.

First payment of the day

The first successful fare payment received through the driver's terminal establishes that the driver has started operating for that day. That event triggers the daily ticket check and, if unpaid, the ticket deduction. Subsequent fares that day do not trigger another ticket.

Operating-day rule

  • Trigger: first successful fare transaction for the driver on the platform operating date.
  • Source: the driver's linked receiving bank account.
  • Destination: the driver's union bank account resolved server-side.
  • Once per day: a database uniqueness rule prevents duplicate ticket charges for the same driver and operating date.
  • Visibility: the driver can see the ticket alongside normal daily fare transactions in their transaction history.
  • Failure handling: ticket payment must have an explicit result; provider uncertainty must not cause a second debit, and a failed or uncertain ticket must not be silently marked paid.

Settlement relationship

The ticket is a separate financial event from the passenger fare. The passenger still pays the fare to the driver through the existing payment flow, while the daily ticket is a driver-side levy routed to the union. The backend resolves both destinations and never accepts either account from the tap request.

Production invariant

Two concurrent first taps must never produce two daily tickets. The ticket record should be created or claimed atomically using driver_id + operating_date as the uniqueness boundary, with provider idempotency protecting the external debit.

Beyond physical cards

Phone-based tap (HCE)

Letting a passenger's own NFC phone initiate payment — not just a physical card — is a real feature, and it can be architected to reuse the exact device-bound-key pattern already built for driver terminals, rather than inventing something new.

The mechanism: Host Card Emulation

Android phones can run an HCE (Host Card Emulation) service inside an app — the phone presents itself to the driver's reader exactly like a physical NFC card at the protocol level. The driver terminal doesn't need to know or care whether it just read a card or a phone.

Worth doing properly, not just the easy version

The naive version has the phone emit a static token, identical to a physical card's UID — which inherits the same cloning risk cards already have. The better version reuses the device-bound key + signed nonce pattern already built for driver terminals: the phone holds a private key in Android Keystore, the reader/backend sends a challenge, the phone signs it live. A cloned static token is replayable; a live signature isn't. Same mechanism, same reasoning, already proven out in the device-binding fix — just applied to the passenger side now.

Platform reality — Android first, iOS is different

Android supports general-purpose third-party HCE apps today — this is straightforwardly buildable as a feature of a passenger app. iOS locks NFC card emulation down much harder; third-party apps generally can't emulate a card the way Android allows. The realistic iOS path is Apple's Express Transit entitlement — a program specifically for transit agencies, requiring an application process with Apple, not just a code change. Practical read: build phone-tap for Android first, treat iOS as its own later effort with its own approval timeline, and keep physical cards as the universal fallback that works on both.

Structural gap this surfaces

Phone-tap requires a passenger-facing app to host the HCE service — and nothing in the Flutter structure so far builds one. vehicle_mode/, agent_ops/, and ops/ are all driver- or staff-facing. A passenger app (or a passenger mode within the same codebase) is new scope, not something this slots into for free.

Schema

credential.type distinguishes card from phone_hce — a card credential carries card_uid, a phone credential carries device_public_key instead. Both are still just rows in the same table; AuthorizeTrip's downstream logic (session check, fallback, trip creation) doesn't change either way.

// challenge-response variant — reader sends a nonce, phone signs it live,
// backend verifies against the stored public key. No static token to clone.
func AuthorizeTripPhone(deviceSignature []byte, challengeNonce, terminalID string) (*Trip, error) {
    if db.NonceSeen(challengeNonce) {
        return nil, errors.New("replay detected")
    }
    credential := db.FindCredentialByChallenge(challengeNonce)
    if credential.Type != "phone_hce" {
        return nil, errors.New("not a phone credential")
    }
    if !verifySignature(credential.DevicePublicKey, challengeNonce, deviceSignature) {
        return nil, errors.New("signature does not match — reject")
    }
    db.MarkNonceUsed(challengeNonce)
    // from here: identical to AuthorizeTrip — session check, fallback, trip creation
    return continueTripAuthorization(credential.IdentityID, terminalID)
}

3 — Driver shift-start session Flutter Go

// routeID is the driver's choice for today — pre-filled with their usual
// route client-side, but this is what actually gets locked in for the shift
func StartDriverSession(driverID, terminalID, routeID string, scan FingerprintScan) (*Session, error) {
    terminal := db.GetTerminal(terminalID)
    if terminal.BoundDriverID != driverID { return nil, errors.New("terminal not bound to this driver") }

    if !db.RouteExists(routeID) { return nil, errors.New("not an admin-defined route") } // drivers pick from existing routes, don't invent one

    identity := db.GetIdentity(driverID)
    daysSince := time.Since(identity.LastVerified).Hours() / 24
    method := "local_match"

    if daysSince > ReverifyWindowDays {
        result := vsp.VerifyFingerprint(scan)
        if !result.Match { return nil, errors.New("re-verification failed") }
        db.UpdateLastVerified(driverID, time.Now())
        method = "live_reverify"
    } else {
        if !matchLocalTemplate(identity.TemplateHash, scan) { return nil, errors.New("fingerprint mismatch") }
    }

    return db.CreateSession(Session{
        DriverID: driverID, TerminalID: terminalID, RouteID: routeID, Token: generateToken(),
        ExpiresAt: time.Now().Add(ShiftTTL), VerifyMethod: method, Status: "active",
    }), nil
}

4 — Trip authorization: replay-checked AND duplicate-tap-checked Flutter Go

Two different protections, doing two different jobs

Nonce replay check stops the exact same signed request being processed twice — a network retry resending an identical payload. It does not stop a second, genuinely different tap (fresh nonce) for the same real boarding event — a driver double-tapping by accident, or a passenger tapping again because the confirmation wasn't visible. That needs a second, independent check: a short-window lookup for a recent successful trip on the same passenger+terminal pair. Both are required; neither substitutes for the other.

func AuthorizeTrip(cardUID, terminalID, nonce string, quote *FareQuote) (*Trip, error) {
    if db.NonceSeen(nonce) { return nil, errors.New("replay detected") } // catches: identical request resent

    credential := db.FindCredentialByCard(cardUID)
    if credential.Status != "active" { return nil, errors.New("card is not active") }

    // catches: a genuinely different tap, same passenger+terminal, seconds apart —
    // short window on purpose, never blocks a real second trip minutes later
    if recent := db.FindRecentSuccessfulTrip(credential.IdentityID, terminalID, 20*time.Second); recent != nil {
        return recent, nil // idempotent response — return the existing trip, don't charge again
    }

    session := db.FindActiveSession(terminalID)
    if session == nil || session.ExpiresAt.Before(time.Now()) { return nil, errors.New("no active driver session") }

    terminal := db.GetTerminal(terminalID)
    payoutAccount := db.GetLinkedAccount(terminal.BoundDriverID)

    var trip Trip
    err := db.WithTx(func(tx) error {
        trip = db.CreateTrip(tx, Trip{
            PassengerID: credential.IdentityID, SessionID: session.ID, EntryTerminal: terminalID,
            Nonce: nonce, Fare: quote.FareAmount, FareSourceType: quote.SourceType, FareSourceID: quote.SourceID,
        })
        // nonce doubles as the idempotency key — stable across a retry, known before
        // this call, so even if this exact call gets retried after a lost response,
        // Moniepoint returns the original result instead of transferring twice
        return moniepoint.Transfer(credential.IdentityID, payoutAccount, trip.Fare, IdempotencyKey(nonce))
    })
    if err != nil { return nil, err }

    db.MarkNonceUsed(nonce)
    return &trip, nil
}

10 — Shift end: reconcile the batch Go

// every allocated card resolves into issued + returned + damaged — no exceptions.
// damaged is tracked separately so a frayed card doesn't look like a missing one
func ReconcileShift(batchID string, quantityReturned, quantityDamaged int, adminID string) (*CardBatch, error) {
    batch := db.GetCardBatch(batchID)
    quantityIssued := db.CountCredentialsIssuedByAgent(batch.AgentID, batch.AllocatedAt, time.Now())

    accounted := quantityIssued + quantityReturned + quantityDamaged
    if accounted != batch.QuantityAllocated {
        db.UpdateCardBatch(batchID, Status: "discrepancy", QuantityReturned: quantityReturned, QuantityDamaged: quantityDamaged)
        checkDiscrepancyPattern(batch.AgentID) // tiered policy — see below
        return nil, errors.New("card count mismatch — flagged for HQ review")
    }

    return db.UpdateCardBatch(batchID, Status: "reconciled", QuantityReturned: quantityReturned, QuantityDamaged: quantityDamaged, ReconciledBy: adminID, ReconciledAt: time.Now()), nil
}

// tier 2 of the policy — pause allocation until a pattern is reviewed
func checkDiscrepancyPattern(agentID string) {
    recent := db.CountDiscrepancies(agentID, last30Days())
    if recent >= 2 {
        db.FlagAgentForReview(agentID) // blocks AllocateCards until HQ clears it
    }
}

Hardware & operations

Terminal hardware, agents & HQ monitoring

Two different "terminal" concepts get used loosely in this project — worth being precise here. The device terminal is the driver's handheld/mounted hardware, bound to exactly one driver (the terminal table). A terminal location is a physical pickup point (Tanke, Challenge) — where field agents are stationed.

Device terminal — the resolved phased plan

This went through real back-and-forth — a DIY ESP32/RPi Zero build was considered and retired once a better-fitting commercial option turned up. Landed here, in order:

  • T1 (now): budget Android device. Mid-range phones with both NFC and a fingerprint sensor already exist in the ₦40k–70k range. Runs the Flutter app directly — no new language, no PAXSTORE review lead time, no procurement uncertainty. Nothing about hardware blocks the pilot from starting.
  • T2: PAX A920 Pro. PCI PTS 5.x SRED-certified, built-in touchscreen, NFC, GPS, 4G — purpose-built for exactly this kind of mobile field commerce, not consumer hardware pressed into service. Transition point once the fleet scales to 5 corridors — by then PAXSTORE developer registration has had time to clear in parallel, and real T1 revenue justifies the higher per-unit cost. One real gap: no confirmed fingerprint sensor on this device — StartDriverSession's verify_method gains a pin_match option alongside local_match/live_reverify, with the device-bound key still anchored in the A920's certified secure processor. Deployment goes through PAX's Developer Portal → PAXSTORE submission (private, fleet-only listing, not public) → a local reseller for procurement — not a full business partnership, but a real registration-and-review process.
  • T4/T5: ODM-customized or fully custom hardware. A real long-term goal, deliberately sequenced late — 12–24+ months of engineering, mandatory NCC type approval for any custom cellular device sold in Nigeria, optional-but-valuable PCI PTS certification if matching A920-level trust assurance matters. Start ODM relationship-building informally during T2–T3 so T4 isn't starting from zero; don't let it compete with T1–T3's actual job, which is proving the software and business model work.

The ESP32/RPi Zero + companion-phone hybrid considered earlier is retired, not built — A920 Pro achieves better durability and real security certification with no new firmware skill required, so the DIY path no longer earns its complexity.

HQ — monitoring only

HQ does not run registration. It's the React + Mapbox admin dashboard — live driver/vehicle positions, session status, revenue, anomaly flags, and the terminal provisioning/rebind console. Its one operational role beyond monitoring is new driver onboarding, kept centralized because it binds physical hardware to a driver — a security-sensitive action, not a customer-service one.

Field agents — fast, distributed, passenger-facing

Agents are stationed at terminal locations and run the same Flutter app in a separate agent mode, gated by an agent login. HQ delivers them physical NFC card stock; agents handle:

  • New passenger registration — identity enrollment, Moniepoint account link, card issuance, on the spot.
  • Lost card recovery — live VSP re-verification, old card voided, new card issued immediately — no trip to HQ, no downtime for the passenger.
  • Immediate customer support — first point of contact for a passenger with a failed tap or a payment question.

Every card an agent issues carries issued_by_agent_id — HQ can see which agent issued which card without being in the loop on the issuance itself. This is what keeps agent-issued cards accountable while the operation stays fast.

Card stock accountability

Agents are allocated a fixed number of blank cards per duty (AllocateCards). At shift end, ReconcileShift checks that issued + returned + damaged = allocated — every card is accounted for, no exceptions. Damaged cards are tracked in their own bucket so a frayed card doesn't read the same as a missing one. A mismatch doesn't get silently absorbed; the batch is flagged discrepancy for HQ review rather than marked reconciled.

Discrepancy policy — tiered, not zero-tolerance

A missing blank card isn't a security event by itself — it's inert until run through live biometric verification, so the real risk is waste or sloppy counting, not fraud. Policy: 1st small discrepancy (1–2 cards) is logged and recounted, no penalty — almost always a counting error. 2+ discrepancies within 30 days auto-flags the agent (checkDiscrepancyPattern) and blocks their next AllocateCards call until HQ reviews it. A pattern across shifts, or one large unexplained gap escalates to a separate investigation — that's a personnel question, not an inventory one.

Terminal activity ping — already covered

The device terminal's existing /location ping feeds terminal_locations — when several device terminals cluster at Tanke, that's the activity signal HQ's live map shows, feeding dead-zone detection. This is separate from and doesn't depend on agents being physically present.

How admin actually gets accessed

A separate URL entirely — its own subdomain, never linked from the customer app, the marketing site, or anywhere public (though worth knowing: an unlisted subdomain still shows up in public certificate transparency logs the moment it gets an SSL cert — this is mild deterrence, not real protection; 2FA and zero public registration are what's actually doing the work). RBAC is now a real schema field, not just a checklist line: identity.admin_tier — ops gets monitoring and read access, super_admin gets provisioning, fare edits, and everything privileged.

Login: WebAuthn/passkeys, not just password + 2FA

Login uses the fingerprint or face sensor already built into the admin's own laptop or phone — Touch ID, Windows Hello, Android's sensor — via the WebAuthn standard. The device generates a private/public key pair; the private key never leaves the device's own secure hardware. Logging in signs a server challenge with that key after a local biometric unlock. The biometric itself never touches the server — only a signed cryptographic proof does.

This isn't a new pattern — it's the same one already proven elsewhere in this system

Device-bound private key, signed challenge-response, biometric never transmitted — this is exactly the mechanism already built for driver terminal device binding and the phone-tap (HCE) design. Admin login reuses a pattern this architecture already trusts, rather than inventing a fourth one. It's also phishing-resistant in a way passwords and SMS codes aren't: the signature is cryptographically bound to the real domain, so a convincing fake login page can't extract a valid one.

Password + 2FA remains the fallback for any device without biometric hardware — not removed, just no longer the primary path. Hardware security keys (YubiKey-style, tapped to confirm login) are worth adding as a stronger optional layer for super_admin specifically, once that circle is small and stable enough to issue physical keys to — real cost per device, only worth it once who holds super-admin isn't still shifting.

Considered and deliberately rejected: retina scanning, or any server-side admin biometric store

Real technology, but it needs dedicated scanner hardware nobody's laptop or phone has — issuing specialized peripherals to admins for marginal gain over WebAuthn isn't worth it, and it breaks checking the dashboard from a phone entirely. More importantly: this platform's whole biometric model deliberately never stores raw biometrics — NIMC/VSP is the external authority, the platform only ever receives a token back. A server-side admin fingerprint database would recreate exactly the centralized biometric honeypot risk the rest of this design goes out of its way to avoid. WebAuthn gets the security benefit without the platform ever becoming a biometric custodian for its own staff.

No public registration, ever — the bootstrap problem and how it's solved

Every admin account has to come from somewhere, but there's no "sign up" form — that would let anyone self-grant access to live driver GPS and fare-editing power. The first account is created once, directly, via a deployment script when the system stands up — not through the app, since the app has no admin yet to authorize creating one. Every account after that is invited by an existing super-admin from inside the dashboard — an invite token, emailed, the new admin registers a passkey (or falls back to password + 2FA) on first use. No self-service path exists at any point after bootstrap.

  • Provider uncertainty is represented as UNKNOWN, never silently converted to failure.
  • Fallback is allowed only when the first payment attempt is known to have failed safely.

Flutter and React are planned client surfaces; neither has been started in the current implementation checkpoint. The current working product is the Go + Gin + PostgreSQL backend.

02APIs & backend logicCovered

Go + Gin. Working backend code currently covers registration, passenger account linking, terminal registration, trip retrieval and a prototype tap calculation path. Authentication, real payment authorization and production tap transaction orchestration are not yet implemented. See the Pseudocode section.

PostgreSQL is implemented with the current users, passenger_accounts, terminals, trips and payments schema. PostGIS, session, credential, route and geospatial tables remain planned. See Data Model and Geospatial Layer.

04Auth & permissionsPartial

Authentication and authorization are intentionally deferred until the current #3–#25 engineering sequence is closed. The current Go API still accepts client-supplied identity identifiers in prototype flows; these must be replaced with server-derived identity after authentication is implemented.

  • Go API in a Docker container — one multi-stage Dockerfile, small final image
  • T0–T2: a single DigitalOcean or Contabo droplet (~$6–12/mo) running the container behind the reverse proxy already planned for TLS
  • React dashboard on Vercel or Netlify's free tier — static build, zero-cost, CDN included for free (feeds layer 10)
  • Driver/agent Flutter apps: direct APK install for the pilot fleet — Play Store distribution is a later-phase decision, not a T1 blocker

A single droplet is "computing," not elastic "cloud" — that's fine for T0–T2. One upgrade worth making early: a managed Postgres (DigitalOcean Managed Database, or Supabase's hosted Postgres with PostGIS support) instead of self-managing Postgres on the same droplet — automatic backups and failover, real risk reduction for a solo builder, modest cost increase. True elastic compute (autoscaling instances) is a T4/T5 decision once multi-city traffic justifies it.

07CI/CD & version controlPartial

Git/GitHub already in use. GitHub Actions already flagged for secret-scanning and vuln-scanning in the security checklist — extend into a real pipeline: push → go vet + go build ./... + tests → merge to main → build Docker image → deploy to the droplet. A simple SSH-deploy step is enough at T0–T2 scale; no need for a heavier CD tool yet.

08Security & row-level securityPartial

General security is the most built-out part of this whole doc — see the Security Checklist and Tracker. Row-level security specifically is optional here, not primary: the Go API is the only thing that ever touches Postgres directly, so RLS would be defense-in-depth against a future authorization bug in Go, not the main control. Worth adding at T3+: enable RLS on trip/identity-adjacent tables, set a per-request session variable (SET LOCAL app.current_driver_id) inside each transaction, write policies against it as a safety net.

09Rate limitingGap

Was a checklist line item, never actually designed. Concrete proposal: a Gin middleware using golang.org/x/time/rate (token bucket), keyed per terminal_id on /tap and per-IP on public endpoints.

func RateLimitByTerminal() gin.HandlerFunc {
    limiters := sync.Map{} // terminal_id → *rate.Limiter
    return func(c *gin.Context) {
        terminalID := c.PostForm("terminal_id")
        limiterAny, _ := limiters.LoadOrStore(terminalID, rate.NewLimiter(rate.Every(time.Second), 5)) // 5 taps/sec burst
        if !limiterAny.(*rate.Limiter).Allow() {
            c.AbortWithStatusJSON(http.StatusTooManyRequests, gin.H{"error": "slow down"})
            return
        }
        c.Next()
    }
}

T2+: push this to the edge (Cloudflare free tier, or nginx limit_req) once a reverse proxy is already in front for TLS anyway.

10Caching & CDNGap

CDN comes free the moment the React dashboard is hosted on Vercel/Netlify (layer 5 decision). Caching is deliberately not for core transactional data — payment and session state must stay live, never cached. The legitimate target is the admin dashboard's aggregate queries (heatmap, corridor stats) — expensive, and don't need per-second freshness. In-memory cache with a 30–60s TTL is enough to start; Redis only once T3's investor-mode dashboard work makes it worth the extra infrastructure.

11Load balancing & scalingGap

Not needed at T0–T2 — a single instance is genuinely fine. One real gotcha worth knowing now, before it's a surprise: /ws/map doesn't horizontally scale for free. Multiple API instances need a shared pub/sub (Redis pub/sub is the standard fix) to fan out position updates across instances, or sticky sessions at the load balancer. This becomes real at T4/T5 multi-city scale-out, not before.

12Error tracking & logsPartial

Mentioned in the security checklist (T3: alerting; T0: redacted structured logging) but never specced with real tools. Concrete proposal: Sentry's free tier (solid Go SDK) for error tracking from T1, not T3 — cheap enough to not wait on. Structured logging via Go's standard log/slog (stdlib, zero new dependency), with the redaction middleware the T0 checklist already calls for. Log viewing via the droplet's journald is enough until multi-instance (layer 11) makes a hosted aggregator worth it.

Fill the loopholes early

Security checklist

Organized by the phase each item belongs to — most security debt gets expensive precisely because it's added after the fact. Items you already have designed (session model, device binding, replay protection) aren't repeated here; this is everything around that core.

T0Foundation — before any feature code
  • TLS on every connection — Flutter↔Go, Go↔Moniepoint/VSP, and the Postgres connection string itself, no exceptions
  • Secrets (Moniepoint keys, VSP credentials, DB creds) in environment variables or a secrets manager — never in source control
  • Postgres service account for the Go API uses least privilege — not a superuser role, scoped to the tables it needs
  • All queries parameterized — no string-concatenated SQL, ever (Go's database/sql placeholders or your ORM's query builder, never raw interpolation)
  • Structured logging that redacts sensitive fields — biometric hashes, tokens, and account numbers never hit plaintext logs
  • Separate credentials for sandbox vs. production — a leaked sandbox key should never be able to touch real money
  • Nonce table + audit log table designed now, not bolted on later
  • Graceful shutdown on SIGINT/SIGTERM — in-flight requests drained, not killed mid-request on every deploy
  • API server has real TLS termination — a reverse proxy or direct cert config, not plain HTTP
T1MVP — real money, real biometrics
  • Raw fingerprint scans discarded immediately after hashing — never written to disk or logs, even temporarily
  • VSP and Moniepoint calls wired behind interfaces (IdentityVerifier, PaymentProcessor) via dependency injection — lets you test failure modes (timeout, rejected verification, double-spend attempt) without hitting real services
  • Moniepoint webhook signature verification — if you consume webhooks for settlement confirmation, verify the HMAC signature on every incoming webhook or you're trusting unauthenticated POST requests to confirm real payments
  • Idempotency key on every Moniepoint call — the tap's nonce, not trip_id (trip_id doesn't exist yet at the moment the call needs to be idempotent). See pseudocode block 4.
  • Short-window duplicate-tap check (FindRecentSuccessfulTrip) — catches a second genuinely different tap for the same boarding event, which nonce replay checking alone does not.
  • Gin binding + validation tags on every request struct — reject malformed input at the handler boundary, before it reaches business logic
  • Rate limiting on /tap and /location — per-terminal and per-IP, so one compromised device can't hammer the API
  • Dependency vulnerability scanning in CI — go mod audit equivalent (govulncheck), flutter pub outdated / audit for Dart packages
  • /tap requires a valid terminal credential — knowing a terminal_id alone isn't enough to authorize a trip
  • The tap flow runs inside a real DB transaction with rollback on failure, not a sequence of independent inserts
T2Terminal network + admin dashboard
  • Admin auth is stronger than driver session auth — this console can rebind terminals and see the full trip ledger
  • Role-based access on the dashboard — ops vs. super-admin, since rebind and reconciliation actions shouldn't be available to every logged-in staff member
  • WebAuthn/passkey login for admin accounts — device biometric, private key never leaves the device — password + 2FA as fallback for devices without biometric hardware
  • Hardware security key option for super_admin, once that circle is stable enough to issue physical keys to
  • CORS locked down on the Go API — only the admin dashboard's actual origin, not a wildcard
  • CSRF protection on the React dashboard if using cookie-based sessions (or stick to bearer tokens in headers to sidestep it)
  • Audit log extended to every privileged action, not just terminal rebinds — who did what, when, from where
T3Admin tooling + investor mode
  • Key rotation policy for device-bound signing keys — define how a terminal's key gets rotated without a full re-provisioning trip
  • Error tracking + alerting wired up (Sentry or similar) — you want to know about failed verifications and rollbacks before a driver complains
  • NDPR data protection impact assessment formalized in writing, not just "we thought about it" — this is the point where you have real biometric data at real volume
  • Anomaly detection thresholds tuned per vehicle class, reviewed against real false-positive rates from T1–T2 usage
T4Partner integration — now genuinely public-facing
  • Partner API uses its own auth scheme (API keys or OAuth client credentials) — separate from driver/passenger session tokens entirely
  • Per-partner rate limiting and usage quotas — one partner's traffic spike shouldn't degrade the whole platform
  • WAF / DDoS protection in front of the public API — you're no longer a closed system only your own app talks to
  • Third-party penetration test before opening the partner API — internal review isn't enough once external code calls your endpoints
  • Incident response plan written down — key rotation steps, session mass-invalidation procedure, who gets notified and when if a breach is suspected
T5City OS — full compliance posture
  • Backup and disaster recovery tested for real — point-in-time Postgres recovery drills, not just "backups are configured"
  • Data retention and right-to-erasure policy — NDPR requires you can actually delete a person's data on request, not just deactivate their account
  • Regular third-party security audits on a schedule, not one-and-done
  • Multi-region security posture reviewed as each new city comes online — don't assume T1's threat model still covers a 5-city footprint

Cutting across every phase

  • Dependency injection for every external integration (VSP, Moniepoint, even Postgres access behind a repository interface) — this is what makes the rest of this checklist actually testable instead of aspirational
  • Least privilege everywhere — database roles, admin permissions, API scopes — default to no access, grant narrowly
  • No secrets in git, checked by a pre-commit hook or CI scan, not just a policy people remember to follow
  • Logs redact sensitive fields by default — build the redaction into your logging middleware once, not per-endpoint
