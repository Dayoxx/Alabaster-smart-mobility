Fixing the gap — part 1

Driver re-verification (session model)

A driver used to bind to a vehicle once, permanently — a stolen or borrowed terminal kept operating as that driver indefinitely. Fix: operating a vehicle requires a short-lived, renewable session.

Risk closed

Whoever physically holds the terminal is no longer automatically "the driver" — a live, expiring session is required, re-confirmed on a schedule and on anomaly.

  • Shift-start check-in — fingerprint matched against the locally cached template, opens a session with a TTL.
  • Session TTL — expires after 8–12 hrs or terminal power cycle; Go rejects trip authorization on expiry.
  • Risk-triggered re-check — GPS jump or impossible velocity forces immediate re-scan mid-session.
  • Periodic re-verification — every 30–90 days, session start requires a live VSP call, not just the cache.
Fixing the gap — part 2

Device binding & receiver-only terminals

Session auth answers "is the right driver operating right now." It doesn't stop someone tampering with where the money goes — this fix closes that separately.

Device-identity binding

Each physical terminal is registered to exactly one driver at provisioning time, keyed by hardware ID — longer-lived than a session.

Receiver-only architecture

On a tap, Flutter captures the NFC UID, signs it with the device-bound key, and relays card_uid + terminal_id + nonce + timestamp. Payout destination is resolved only server-side, from the Postgres binding record.

Net effect

There is nothing on the device to edit, root, or reflash to redirect funds — the routing decision was never on the device.

Replay protection

Every tap carries a single-use signed nonce; Go rejects any nonce already consumed.

Rebinding is privileged and re-verified

Rebinding a terminal requires an admin action and the new driver's fresh fingerprint — never just a database field toggle.

Transaction lifecycle

Payment flow

1 — Tap

Flutter captures NFC card + signs a nonce, sends to Go over HTTPS with pickup coordinates.

2 — Identify & validate session

Go looks up the credential, checks the terminal's active session and expiry.

3 — Fallback chain

Passenger's linked accounts tried in priority order until one has sufficient balance.

4 — Moniepoint executes

Debits passenger, credits the driver account resolved server-side from the terminal binding. Settles under 5s via NIP rails.

5 — Geo + commit

Trip written with pickup_point geometry, corridor stats updated, WebSocket broadcasts the new position to the admin map.

On failure — automatic rollback

Postgres transaction rolls back entirely. Passenger balance untouched, nonce not consumed, scanner gets a retry response.

Reference flows

Pseudocode

Flutter → Go over HTTPS. Go owns every write to Postgres. Nothing runs payout logic on-device.

1 — Identity enrollment Go

// slow path, once per person
func EnrollIdentity(scan FingerprintScan, role Role) (*Identity, error) {
    result := vsp.VerifyFingerprint(scan)
    if result.Confidence < Threshold {
        return nil, errors.New("low confidence, retry")
    }
    template := deriveDeviceBoundTemplate(scan)
    identity := db.CreateIdentity(Identity{
        NINRef: result.NINToken, TemplateHash: hash(template),
        Role: role, LastVerified: time.Now(),
    })
    if role == Driver { requireVehicleLink(identity.ID) }
    return identity, nil
}

2 — Terminal provisioning & rebind Go React

func ProvisionTerminal(serial, driverID, adminID string) (*Terminal, error) {
    return db.CreateTerminal(Terminal{HardwareSerial: serial, BoundDriverID: driverID, BoundAt: time.Now(), BoundByAdmin: adminID})
}

// requires the NEW driver's fresh fingerprint — not just an admin toggle
func RebindTerminal(terminalID string, newDriverScan FingerprintScan, adminID string) error {
    result := vsp.VerifyFingerprint(newDriverScan)
    if !result.Match { return errors.New("new driver verification failed") }
    return db.UpdateTerminalBinding(terminalID, result.IdentityID, adminID)
}

3 — Driver shift-start session Flutter Go

func StartDriverSession(driverID, terminalID string, scan FingerprintScan) (*Session, error) {
    terminal := db.GetTerminal(terminalID)
    if terminal.BoundDriverID != driverID { return nil, errors.New("terminal not bound to this driver") }

    identity := db.GetIdentity(driverID)
    daysSince := time.Since(identity.LastVerified).Hours() / 24
    method := "local_match"

    if daysSince > ReverifyWindowDays {
        result := vsp.VerifyFingerprint(scan)
        if !result.Match { return nil, errors.New("re-verification failed") }
        db.UpdateLastVerified(driverID, time.Now())
        method = "live_reverify"
    } else {
        if !matchLocalTemplate(identity.TemplateHash, scan) { return nil, errors.New("fingerprint mismatch") }
    }

    return db.CreateSession(Session{
        DriverID: driverID, TerminalID: terminalID, Token: generateToken(),
        ExpiresAt: time.Now().Add(ShiftTTL), VerifyMethod: method, Status: "active",
    }), nil
}

4 — Trip authorization + replay check Flutter Go

func AuthorizeTrip(cardUID, terminalID, nonce string) (*Trip, error) {
    if db.NonceSeen(nonce) { return nil, errors.New("replay detected") }
    credential := db.FindCredentialByCard(cardUID)
    if credential.Status != "active" { return Fallback(terminalID) }
    session := db.FindActiveSession(terminalID)
    if session == nil || session.ExpiresAt.Before(time.Now()) { return nil, errors.New("no active driver session") }

    terminal := db.GetTerminal(terminalID)
    payoutAccount := db.GetLinkedAccount(terminal.BoundDriverID)

    trip := db.CreateTrip(Trip{PassengerID: credential.IdentityID, SessionID: session.ID, EntryTerminal: terminalID, Nonce: nonce, Fare: calculateFare(terminalID)})
    moniepoint.Transfer(credential.IdentityID, payoutAccount, trip.Fare)
    db.MarkNonceUsed(nonce)
    return trip, nil
}

5 — Fallback chain Flutter

func Fallback(terminalID string) (*Trip, error) {
    methods := []string{"pin_entry", "ussd_code", "fingerprint_scan"}
    for _, m := range methods {
        if result := tryMethod(m, terminalID); result.Success { return result.Trip, nil }
    }
    return nil, errors.New("manual driver override — cash, flagged for reconciliation")
}

6 — Centralized ops: new driver registration Flutter (ops mode) Go

// run by HQ ops staff, not field agents — this binds hardware to a driver,
// which is a security-sensitive action kept centralized on purpose
func RegisterNewDriver(scan FingerprintScan, vehicle VehicleDetails, terminalSerial, adminID string) (*Driver, error) {
    identity, err := EnrollIdentity(scan, Driver)
    if err != nil { return nil, err }

    v := db.CreateVehicle(Vehicle{OperatorID: identity.ID, PlateRef: vehicle.Plate, Class: vehicle.Class})
    terminal, err := ProvisionTerminal(terminalSerial, identity.ID, adminID)
    if err != nil { return nil, err }

    return &Driver{Identity: identity, Vehicle: v, Terminal: terminal}, nil
}

7 — Field agent: new passenger registration Flutter (agent mode) Go

// run by a field agent at a terminal location, from card stock HQ delivered them
func RegisterPassenger(scan FingerprintScan, bank BankDetails, newCardUID, agentID string) (*Identity, *Credential, error) {
    agent := db.GetIdentity(agentID)
    if agent.Role != Agent { return nil, nil, errors.New("only agents can register passengers") }

    identity, err := EnrollIdentity(scan, Passenger)
    if err != nil { return nil, nil, err }

    db.LinkAccount(identity.ID, bank)
    cred := issueCard(identity.ID, newCardUID, agentID) // traceable to the issuing agent
    return identity, cred, nil
}

8 — Field agent: lost card recovery Flutter (agent mode) Go

// the whole point of the agent network — a passenger gets a working card back
// on the spot, at whichever terminal location they happen to be at
func ReissueCard(claimedIdentityID string, freshScan FingerprintScan, newCardUID, agentID string) (*Credential, error) {
    result := vsp.VerifyFingerprint(freshScan) // live check — agent hardware never enrolled this person
    if !result.Match { return nil, errors.New("identity mismatch — not issuing a card") }
    if result.IdentityID != claimedIdentityID { return nil, errors.New("scan does not match the account being recovered") }

    db.VoidCredential(claimedIdentityID)
    return issueCard(claimedIdentityID, newCardUID, agentID), nil
}

9 — Shift start: allocate cards to an agent Flutter (agent mode) Go

func AllocateCards(agentID string, quantity int, adminID string) (*CardBatch, error) {
    return db.CreateCardBatch(CardBatch{
        AgentID: agentID, QuantityAllocated: quantity,
        Status: "open", AllocatedAt: time.Now(),
    }), nil
}

10 — Shift end: reconcile the batch Go

// every allocated card resolves into issued + returned + damaged — no exceptions.
// damaged is tracked separately so a frayed card doesn't look like a missing one
func ReconcileShift(batchID string, quantityReturned, quantityDamaged int, adminID string) (*CardBatch, error) {
    batch := db.GetCardBatch(batchID)
    quantityIssued := db.CountCredentialsIssuedByAgent(batch.AgentID, batch.AllocatedAt, time.Now())

    accounted := quantityIssued + quantityReturned + quantityDamaged
    if accounted != batch.QuantityAllocated {
        db.UpdateCardBatch(batchID, Status: "discrepancy", QuantityReturned: quantityReturned, QuantityDamaged: quantityDamaged)
        checkDiscrepancyPattern(batch.AgentID) // tiered policy — see below
        return nil, errors.New("card count mismatch — flagged for HQ review")
    }

    return db.UpdateCardBatch(batchID, Status: "reconciled", QuantityReturned: quantityReturned, QuantityDamaged: quantityDamaged, ReconciledBy: adminID, ReconciledAt: time.Now()), nil
}

// tier 2 of the policy — pause allocation until a pattern is reviewed
func checkDiscrepancyPattern(agentID string) {
    recent := db.CountDiscrepancies(agentID, last30Days())
    if recent >= 2 {
        db.FlagAgentForReview(agentID) // blocks AllocateCards until HQ clears it
    }
}
Hardware & operations

Terminal hardware, agents & HQ monitoring

Two different "terminal" concepts get used loosely in this project — worth being precise here. The device terminal is the driver's handheld/mounted hardware, bound to exactly one driver (the terminal table). A terminal location is a physical pickup point (Tanke, Challenge) — where field agents are stationed.

Device terminal — build options

  • T1 default: budget Android device. Mid-range phones with both NFC and a fingerprint sensor already exist in the ₦40k–70k range. Runs your Flutter app directly — no new language, no embedded hardware R&D.
  • T4/T5 option: custom hardware. ESP32/RPi Zero + PN532 NFC + fingerprint module + GSM + GPS, running embedded C/C++ or MicroPython. Only worth it once device cost at scale is the actual bottleneck.

HQ — monitoring only

HQ does not run registration. It's the React + Mapbox admin dashboard — live driver/vehicle positions, session status, revenue, anomaly flags, and the terminal provisioning/rebind console. Its one operational role beyond monitoring is new driver onboarding, kept centralized because it binds physical hardware to a driver — a security-sensitive action, not a customer-service one.

Field agents — fast, distributed, passenger-facing

Agents are stationed at terminal locations and run the same Flutter app in a separate agent mode, gated by an agent login. HQ delivers them physical NFC card stock; agents handle:

  • New passenger registration — identity enrollment, Moniepoint account link, card issuance, on the spot.
  • Lost card recovery — live VSP re-verification, old card voided, new card issued immediately — no trip to HQ, no downtime for the passenger.
  • Immediate customer support — first point of contact for a passenger with a failed tap or a payment question.

Every card an agent issues carries issued_by_agent_id — HQ can see which agent issued which card without being in the loop on the issuance itself. This is what keeps agent-issued cards accountable while the operation stays fast.

Card stock accountability

Agents are allocated a fixed number of blank cards per duty (AllocateCards). At shift end, ReconcileShift checks that issued + returned + damaged = allocated — every card is accounted for, no exceptions. Damaged cards are tracked in their own bucket so a frayed card doesn't read the same as a missing one. A mismatch doesn't get silently absorbed; the batch is flagged discrepancy for HQ review rather than marked reconciled.

Discrepancy policy — tiered, not zero-tolerance

A missing blank card isn't a security event by itself — it's inert until run through live biometric verification, so the real risk is waste or sloppy counting, not fraud. Policy: 1st small discrepancy (1–2 cards) is logged and recounted, no penalty — almost always a counting error. 2+ discrepancies within 30 days auto-flags the agent (checkDiscrepancyPattern) and blocks their next AllocateCards call until HQ reviews it. A pattern across shifts, or one large unexplained gap escalates to a separate investigation — that's a personnel question, not an inventory one.

Terminal activity ping — already covered

The device terminal's existing /location ping feeds terminal_locations — when several device terminals cluster at Tanke, that's the activity signal HQ's live map shows, feeding dead-zone detection. This is separate from and doesn't depend on agents being physically present.

Key packages

  • nfc_manager — NFC card capture
  • local_auth — device fingerprint sensor
  • flutter_secure_storage — cached template + device key, never plain prefs
  • geolocator + flutter_background_service — GIS ping loop, works backgrounded
  • dio — HTTP client, signing interceptor in core/network
  • flutter_riverpod — session/connectivity state
Why nonce generation lives client-side

The nfc_tap feature signs each nonce with the device-bound key before sending — a cloned request without the real key's signature gets rejected, even if it copies a nonce value.

One app, not three

Identity, session, device binding, the signed nonce, and fallback chain are identical across vehicle classes — forking them per vehicle would put the most security-sensitive code in multiple places. Only the trip-flow UI branches, via vehicle.class. Taxi gets no first-party UI here — per the T4 plan, taxi drivers stay on their existing partner app; this system only supplies identity verification behind the scenes.

Organized by the phase each item belongs to — most security debt gets expensive precisely because it's added after the fact. Items you already have designed (session model, device binding, replay protection) aren't repeated here; this is everything around that core.

T0Foundation — before any feature code
  • TLS on every connection — Flutter↔Go, Go↔Moniepoint/VSP, and the Postgres connection string itself, no exceptions
  • Secrets (Moniepoint keys, VSP credentials, DB creds) in environment variables or a secrets manager — never in source control
  • Postgres service account for the Go API uses least privilege — not a superuser role, scoped to the tables it needs
  • All queries parameterized — no string-concatenated SQL, ever (Go's database/sql placeholders or your ORM's query builder, never raw interpolation)
  • Structured logging that redacts sensitive fields — biometric hashes, tokens, and account numbers never hit plaintext logs
  • Separate credentials for sandbox vs. production — a leaked sandbox key should never be able to touch real money
  • Nonce table + audit log table designed now, not bolted on later
T1MVP — real money, real biometrics
  • Raw fingerprint scans discarded immediately after hashing — never written to disk or logs, even temporarily
  • VSP and Moniepoint calls wired behind interfaces (IdentityVerifier, PaymentProcessor) via dependency injection — lets you test failure modes (timeout, rejected verification, double-spend attempt) without hitting real services
  • Moniepoint webhook signature verification — if you consume webhooks for settlement confirmation, verify the HMAC signature on every incoming webhook or you're trusting unauthenticated POST requests to confirm real payments
  • Idempotency keys on every Moniepoint call (trip_id + timestamp) — already in your pseudocode, don't skip it under deadline pressure
  • Gin binding + validation tags on every request struct — reject malformed input at the handler boundary, before it reaches business logic
  • Rate limiting on /tap and /location — per-terminal and per-IP, so one compromised device can't hammer the API
  • Dependency vulnerability scanning in CI — go mod audit equivalent (govulncheck), flutter pub outdated / audit for Dart packages
T2Terminal network + admin dashboard
  • Admin auth is stronger than driver session auth — this console can rebind terminals and see the full trip ledger
  • Role-based access on the dashboard — ops vs. super-admin, since rebind and reconciliation actions shouldn't be available to every logged-in staff member
  • Two-factor authentication on admin accounts specifically
  • CORS locked down on the Go API — only the admin dashboard's actual origin, not a wildcard
  • CSRF protection on the React dashboard if using cookie-based sessions (or stick to bearer tokens in headers to sidestep it)
  • Audit log extended to every privileged action, not just terminal rebinds — who did what, when, from where
T3Feeder layer + investor mode
  • Key rotation policy for device-bound signing keys — define how a terminal's key gets rotated without a full re-provisioning trip
  • Error tracking + alerting wired up (Sentry or similar) — you want to know about failed verifications and rollbacks before a driver complains
  • NDPR data protection impact assessment formalized in writing, not just "we thought about it" — this is the point where you have real biometric data at real volume
  • Anomaly detection thresholds tuned per vehicle class, reviewed against real false-positive rates from T1–T2 usage
T4Partner integration — now genuinely public-facing
  • Partner API uses its own auth scheme (API keys or OAuth client credentials) — separate from driver/passenger session tokens entirely
  • Per-partner rate limiting and usage quotas — one partner's traffic spike shouldn't degrade the whole platform
  • WAF / DDoS protection in front of the public API — you're no longer a closed system only your own app talks to
  • Third-party penetration test before opening the partner API — internal review isn't enough once external code calls your endpoints
  • Incident response plan written down — key rotation steps, session mass-invalidation procedure, who gets notified and when if a breach is suspected
T5City OS — full compliance posture
  • Backup and disaster recovery tested for real — point-in-time Postgres recovery drills, not just "backups are configured"
  • Data retention and right-to-erasure policy — NDPR requires you can actually delete a person's data on request, not just deactivate their account
  • Regular third-party security audits on a schedule, not one-and-done
  • Multi-region security posture reviewed as each new city comes online — don't assume T1's threat model still covers a 5-city footprint

Cutting across every phase

  • Dependency injection for every external integration (VSP, Moniepoint, even Postgres access behind a repository interface) — this is what makes the rest of this checklist actually testable instead of aspirational
  • Least privilege everywhere — database roles, admin permissions, API scopes — default to no access, grant narrowly
  • No secrets in git, checked by a pre-commit hook or CI scan, not just a policy people remember to follow
  • Logs redact sensitive fields by default — build the redaction into your logging middleware once, not per-endpoint

Beyond the architecture

Open gaps

The technical scope is solid. These are the things that don't show up in a schema diagram but will stall a launch if left until the last minute.

GAPOffline resilience
  • Flutter app queues signed trip requests locally when offline, syncs on reconnect
  • Nonce/replay logic tolerates delayed submission, not just live taps
  • Design this before T1 ships — retrofitting later means touching almost every part of the tap flow
GAPLegal & regulatory
  • Confirm CBN Payment Service Provider licensing category for a routing-only, zero-custody platform — with an actual legal read, not just architectural reasoning
  • Terms of service and a privacy policy matching your real NDPR posture
  • Written dispute/refund policy — what happens when a passenger claims a double charge
GAPAgent network operations
  • Agent onboarding and accountability process — separate from HQ staff, separate from drivers
  • Card batch allocation + shift reconciliation implemented — designed (AllocateCards / ReconcileShift), not yet built
  • Agent enrollment device — hardware choice deferred, to be decided
  • Agent performance visibility on the HQ dashboard — cards issued, response time, coverage per terminal location
GAPTesting strategy
  • Integration tests for the full tap → debit → payout chain, not just unit tests on individual functions
  • Load testing — simultaneous taps during rush hour, not just sequential requests
  • Device testing across the actual range of cheap Android hardware drivers will own
GAPFare engine
  • Move off a flat ₦200 fare before multi-corridor expansion (T2) — route or distance-band based fare table
GAPFinancial reconciliation & reporting
  • Daily settlement reports
  • Driver payout statements a driver can actually read
  • Tax/reporting obligations on platform fee income identified and tracked
GAPSupport & operations
  • Process for a broken terminal mid-shift — driver's actual next step
  • Escalation path beyond the agent — who a passenger reaches for a dispute the agent can't resolve
