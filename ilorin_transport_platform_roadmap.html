What we're building
A cashless transport platform for Ilorin

One app that serves both passengers and drivers. Passengers link their bank accounts and tap to pay. Drivers receive money instantly to any Nigerian bank or wallet. The platform earns a small fee per transaction. No money is held — it flows directly from passenger to driver via Moniepoint's infrastructure.

Starting with Keke NAPEP on Ilorin's busiest corridors, expanding to BRT when the city is ready.

Core principles
Zero money held
The platform is a routing layer, not a wallet. Money moves directly from passenger's bank to driver's account. No CBN stored-value license required at this stage.
One bridge — Moniepoint
A single API handles both collection (from passenger's linked bank) and disbursement (to driver's any-bank account). One integration, every Nigerian account reachable via NIP rails.
Multi-account fallback
Passengers link multiple accounts with a priority order. If the primary account has insufficient funds, the next account is tried automatically. A seamless tap, always.
Same app, two roles
Passengers and drivers use the same Flutter app. Role is determined at registration. The UI surfaces different screens but the underlying auth and data model are unified.

Key backend decisions
Go for the API
Handles concurrent tap requests with low latency. Compiles to a single binary. Easy to deploy on a cheap VPS. Aligns with what you're already learning.
PostgreSQL transactions for safety
Every tap runs inside a DB transaction. If Moniepoint fails to pay the driver, the passenger's balance is rolled back automatically. No money is lost.
BEGIN TRANSACTION
deduct passenger balance
call Moniepoint API
if success → COMMIT + log trip
if fail → ROLLBACK (balance restored)
END
Idempotency on every payout
Every Moniepoint API call includes a unique reference (trip_id + timestamp). If a network glitch triggers a retry, Moniepoint detects the duplicate and pays only once.

Transaction lifecycle
What happens when a passenger taps
1. Scanner tap
NFC scanner on Keke reads passenger card. Sends HTTP POST to your Go API over GSM data.
POST /tap
{ "card_id": "ABC123", "terminal_id": "KEKE_001", "amount": 200 }
2. Identify & validate
API looks up passenger from card_id. Looks up driver from terminal_id. Validates both accounts are active.
3. Fallback chain
API tries passenger's accounts in priority_order. Calls Moniepoint A2A debit on Account 1. If insufficient funds, tries Account 2. Continues until success or all accounts exhausted.
4. Moniepoint executes
Moniepoint debits passenger's bank (₦200) and credits driver's registered account (₦190) via NIP rails. Platform keeps ₦10. Settles in under 5 seconds.
5. Commit & notify
PostgreSQL transaction commits. Trip record written. Both passenger and driver receive instant push notification.
Passenger: "₦200 paid · Keke NAPEP · Tanke → Challenge"
Driver: "₦190 received to your Access account"
On any failure — automatic rollback
If Moniepoint fails at any point, the PostgreSQL transaction rolls back. Passenger's balance is untouched. No money lost. Scanner receives a "retry" response.
Multi-account fallback
Passenger has 3 accounts linked
Fallback logic (priority_order)
1. Try GTBank (priority 1) → ₦0 balance → skip
2. Try OPay (priority 2) → ₦450 → sufficient → debit ₦200 ✓
3. PalmPay (priority 3) → not reached

Passenger notified: "Paid from OPay · GTBank had insufficient funds"
Product phases
Three-phase roadmap
Phase 1 NFC tap-to-pay · Keke NAPEP pilot Month 1–4
  • Go REST API with /tap, /register, /link-account, /trips endpoints
  • PostgreSQL schema — users, passenger_accounts, terminals, trips, notifications
  • Moniepoint API integration — A2A collection and instant disbursement
  • NFC scanner hardware on 10–20 Keke (PN532 + SIM + GPS, ~₦20,000/unit)
  • Standard NFC card per passenger (₦500–1,000/card, no biometrics yet)
  • Multi-account fallback chain logic
  • Flutter app — passenger view (linked accounts, trip history) + driver view (earnings)
  • Push notifications on every transaction for both roles
  • Pilot route: Tanke ↔ Challenge corridor
Phase 2 Scale + USSD + analytics Month 5–9
  • USSD integration via Africa's Talking — balance check, account linking for non-smartphone users
  • Expand to 5 major Ilorin corridors — Fate Road, Offa Garage, Kulende, Asa Dam
  • Real-time driver earnings dashboard with weekly and monthly analytics
  • Admin dashboard — live trip map, revenue per route, failed transaction monitoring
  • Onboard first Keke cooperative formally — union partnership, group scanner deployment
  • Apply for Tony Elumelu Foundation, GIZ, and World Bank MOBILIST grants
  • Approach Kwara State Ministry of Transport with pilot data
Phase 3 Biometric · BRT · expansion Month 10+
  • Fingerprint biometric authentication — replace NFC card tap with finger press on scanner
  • Biometric enrollment infrastructure at BRT terminals and agent points
  • NDPR-compliant on-device fingerprint storage (template never leaves scanner chip)
  • BRT integration — same backend, new terminal_type, payout routes to company account
  • Route planning layer — OpenStreetMap + OSRM for passenger journey planning
  • Expand to other Kwara towns — Offa, Erin-Ile, Ajase-Ipo
  • Open platform API — let other transport operators integrate their vehicles

What to build first
Week 1–2 · Wallet API in Go
Build POST /tap with PostgreSQL. No Moniepoint yet — simulate the payment. Get the rollback logic working perfectly.
Week 3–4 · Moniepoint sandbox
Create Moniepoint test account. Wire the disbursement API into /tap. Test real (fake) money flowing to a test driver account.
Week 5–6 · Scanner simulation
Write a script that POSTs to /tap to simulate a scanner. Test the full flow end to end — tap → debit → payout → notification → log.
Week 7–8 · Flutter app MVP
Passenger sees their linked accounts and trip history. Driver sees today's earnings. That's the entire MVP. Ship it.
